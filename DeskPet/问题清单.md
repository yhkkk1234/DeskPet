### 3. `core/soul/innate_tendency.rs:65` — 宏内变量捕获错误

```rust
macro_rules! perturb {
    ($v:expr, $rng:expr) => {{
        let delta: f64 = rng.gen_range(-0.08_f64..0.08_f64).abs(); // ← 读的是外层 rng
        if $rng.gen_bool(0.5) { ($v + delta).min(1.0) } else { ($v - delta).max(0.0) }
```

- **问题**: `delta` 读取的是外层函数作用域的 `rng`，而非宏参数 `$rng`。当前测试恰好传了同一个变量，所以测试通过了。但如果将来随机源分离，这里会静默使用错误的 RNG。
- **影响**: 轻微——目前无实际影响，但违反宏卫生原则。
- **✅ 审查结果**: **已修复**。`rng.gen_range(...)` → `$rng.gen_range(...)`，宏参数正确传递。

## 🟠 主要级（逻辑错误 / 行为不符合预期）

### 4. `commands/chat_commands.rs:114-151` — 情感事件双重应用

- **问题**: `chat_with_pet` 中对情感分析结果应用了两次：
  1. 第 114-118 行：`apply_emotional_event`，使用事件类型预计算 delta（如 NormalChat = 2.0 × intensity）
  2. 第 150-151 行：`sentiment_love_hate` 直接加到 `sensibility` 上
- **影响**: 宠物对一次对话产生双重情感响应。基线事件和 AI 的分析提示可能相互矛盾（如事件类型是 NormalChat，但 AI 认为用户不开心）。
- **✅ 审查结果**: **已修复**（2026-04-25，P8 阶段）。详细分析如下：

#### 矛盾分析

原始代码对 Sensibility 产生了**两次冲击**：

| 来源 | 值 | 说明 |
|------|----|------|
| `apply_emotional_event` → `love_hate_delta` | 事件类型计算，如 NormalChat = 2.0 × intensity | 设计文档 §5.7.2 定义的硬编码表 |
| 直接 `sensibility.apply_event(sentiment_love_hate)` | AI 分析给出，范围 -5.0 ~ +5.0 | SentimentAnalyzer 额外产出的字段 |

两者可能矛盾：AI 判定用户不开心（hint = -3.0），但事件类型是 NormalChat（delta = +0.6），Sensibility 同时收到 +0.6 和 -3.0。

同时 `apply_emotional_event` 还对 Impression 写入**固定的 agreeableness ±3/±2**，与后续 AI 分析的 6 维 delta 冲突。

#### 设计文档 §5.7.3 的意图

```
AI 对话后分析 → 解析 AI 返回 → 生成 EmotionalEvent + ImpressionEvent
```

设计文档要求一次 AI 调用产出两个事件，但没有明确说 `love_hate_hint`（AI 直接给的爱恨值）应该替代还是叠加 `EmotionalEvent.calculate_deltas()`（事件类型硬编码的 delta）。

#### 采用方案：AI 主导 + 硬编码保留 baseline

在对话流程中，不再调用 `apply_emotional_event`（该方法保留给 timeline / ghost_commands 等非 AI 场景）。改为：

- **Sensibility**：AI 的 `love_hate_hint` 作为唯一情绪输入（不再叠加硬编码事件表 delta）
- **Baseline**：从 `EmotionalEvent.baseline_delta` 保留里程碑偏移（仅 FirstConversation / BirthdayCelebrated 等非零）
- **Impression**：AI 的 6 维分析作为唯一印象输入（不再叠加硬编码 agreeableness ±3/±2）

改动文件：`chat_commands.rs`（删除内层 `apply_emotional_event` 调用 + 重构外层 ghost 锁为单一路径 + DB 持久化使用真实 `baseline_delta`）

#### 效果对比

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 单次对话 Sensibility 冲击次数 | 3 次 | 1 次 (+ spring) |
| 单次对话 Impression 冲击次数 | 2 次 | 1 次 |
| 普通聊天爱恨变动 | ~4~8 | ~2~5 |
| 吵架一次好感跌幅 | ~16 | ~4 |

#### 备选方案（未采用）

1. **方案 A — 移除 `apply_emotional_event`，仅用 AI 分析结果**：丢失 `baseline_delta`
2. **方案 B — 拆分 `apply_emotional_event` 为 sensibility + impression 两方法**：增加维护心智负担
3. **方案 C — AI 额外返回 `baseline_delta`**：理想方案，但 Prompt 稳定性未验证，工程量大

### 5. `commands/chat_commands.rs:269` — 事件强度计算不对称


### 6. `core/memory/memory_base.rs:11` — last_accessed_at 不持久化

- **问题**: `MemoryBase.last_accessed_at` 仅在内存中维护，`database.rs` 的查询函数读数据库后不更新 `LastAccessedAt` 列。
- **影响**: 重启后所有记忆的 `last_accessed_at` 均为创建时间，依赖此字段的衰减/老化逻辑（如经验熟练度衰减）会得出错误结论。
- **✅ 审查结果**: **已修复**。在 `Database` 中新增 `touch_memory_accessed()` 方法，并在 `MemoryService::get_memories_for_context()` 中调用，每次加载记忆上下文后自动更新 `LastAccessedAt` 列。

### 7. `commands/screenshot_commands.rs:167-172` vs `services/sentiment_service.rs:85-90` — 印象 delta clamp 范围不一致

- **问题**: `curiosity_background_analyze` 中 ImpressionEvent delta clamp 到 `-1.0..1.0`，而 `SentimentAnalyzer::analyze` 中 clamp 到 `-3.0..3.0`。尽管两者各自与 system prompt 要求匹配，但对于 `Impression.apply_event` 来说，好奇心分析的贡献始终是对话情感分析的 ~1/3。
- **影响**: 好奇心背景观察对主人印象的影响力远小于直接对话分析，用户可能无法直观感知这种差异。
- **⏭️ 审查结果**: **跳过（设计意图）**。好奇心观察（被动、间接）和对话分析（主动、直接）本就应有不同影响力权重。当前 clamp 范围与 system prompt 指令一致，属于有意设计而非 bug。未来若有需求可调整。

### 8a. `composables/useChat.ts:152,167` — 消息持久化竞态导致 AI 丢失对话上下文

- **问题**: `pushUserMessage` 和 `pushPetMessage` 中调用 `persistMessage` 未加 `await`（fire-and-forget）。导致以下时序：
  1. 用户发送"早啊" → `pushUserMessage` → `persistMessage('user', '早啊')` 异步启动（未 await）
  2. `invoke('chat_with_pet')` 开始 → AI 流式生成 → `emit("chat:complete")` → `pushPetMessage(response)` → `persistMessage('pet', response)` 异步启动（未 await）
  3. `emit("chat:post-processed")` → `chatLoading = false` → 用户发送"啊，正在写呢"
  4. 第二次 `chat_with_pet` 加载 `ChatMessages` 表 → 第一条 AI 回复可能尚未落库
  5. AI 看到不完整上下文（可能是空历史或仅用户消息），重新生成"打招呼"式回复
- **影响**: 连续对话中 AI 感知不到之前说了什么，重复同一话题或重新打招呼
- **✅ 已修复（P17）**: 后端 `chat_with_pet` 和 `analyze_screenshot` 在 emit 事件前直接写入 `ChatMessages` 表，消除竞态。前端 `pushUserMessage`/`pushPetMessage` 中移除 `persistMessage` 调用。

### 8b1. `data/database.rs:439` — load_chat_history 排序方向错误

```sql
SELECT ... FROM ChatMessages WHERE GhostId = ?1 ORDER BY CreatedAt ASC LIMIT ?2
```

- **问题**: `ASC LIMIT 20` 返回的是 DB 中**最早**的 20 条消息，不是**最新**的 20 条。当聊天记录总量超过 20 条后，`LIMIT` 砍掉的是最新消息，AI 永远看不到最近几轮对话。
- **影响**: 这是"间歇性回答不对题"的根因。对话短时正常，超过一定轮数后 AI 感知不到最新上下文，表现为重新打招呼或答非所问。
- **✅ 已修复（P17）**: `ASC` → `DESC`，取结果后 `.reverse()` 保持 chronological 顺序。同时 `chat_with_pet` 的 limit 从 10 提升到 20，支持更长对话。

### 8b2. `composables/useChat.ts:57` — loadHistory 未映射 assistant→pet

## 🔵 改进建议

### A. 数据库迁移版本管理
当前迁移脚本在 `Database::new()` 中通过硬编码的 SQL 文件路径执行。建议引入版本号表追踪已应用的迁移，以便未来安全地追加新迁移。

### B. ContextWindow 的 Token 估算
```rust
let estimated_tokens = content.len() / 2; // 字节数/2，对中文不准确
```
- **修复前**: 对于中文文本（UTF-8 每个汉字 3 字节），10 个汉字的消息估算为 15 tokens，而多数 tokenizer 实际约为 10-12 tokens。偏差约 30%。
- **✅ 已修复（P9）**: 改用字符-aware 混合估算法——CJK字符≈1.5 tokens，ASCII≈0.3 tokens，用 `estimate_tokens()` 替代 `bytes/2`。

### C. 截图高 DPI 适配
`capture_rect` 中 `GetDIBits` 对于 DPI 缩放 > 100% 的显示器，可能需要先调用 `SetThreadDpiAwarenessContext` 确保获取物理像素而非逻辑像素。目前在高 DPI 系统上截图区域可能偏移。

### D. 气泡对话加载性能
`load_chat_history` 每次加载最多 100 条消息并全部渲染到 Vue 的 `chatMessages` 数组中。随着时间增长，100 条消息的 DOM 渲染可能影响性能。建议实现虚拟滚动或延迟加载。

### E. 单元测试覆盖
当前 rust 后端有 32 个测试（集中在 core 模块），`services/` 和 `commands/` 层基本无测试。建议补充：
- `MemoryService` 的 CRUD 集成测试
- `AIService` mock 测试
- `TimelineService` 的 tick 逻辑测试
- `database.rs` 的 SQL 语句正确性测试

### F. AI配置结构设计局限性
当前采用"一个API Endpoint + 一种API Key + 多种模型"的结构，所有功能（对话/识图/绘图）共享同一个endpoint和api_key。
- **局限性**:
  - 无法对接本地Stable Diffusion/ComfyUI（endpoint不同于聊天服务）
  - 无法混合使用不同服务商（如DeepSeek对话 + GPT-4o识图 + 本地SD绘图）
  - 只适合OpenRouter等一站式多模型云服务商
- **建议**: 分两步渐进式改进
  1. 第一步（当前执行）：绘图配置独立化——新增 `image_gen_endpoint` + `image_gen_api_key`，对话/识图继续共享
  2. 第二步（暂缓）：识图配置独立化——等实际遇到"对话用A服务、识图用B服务"场景时再拆
- **优先级**: 中等（当前架构可用但不够灵活）
- **状态**: 第一步已执行（P10阶段）
